2 · PART 1 · INVERTED INDEX

Dictionary 與 Postings List

Dictionary：先找到 term

Dictionary 存所有不重複的 terms（vocabulary），每個 term 記著 df（幾篇文件含有它）和它的 postings 放在哪裡。查詢時先查 dictionary：查不到就代表沒有任何文件含有這個詞，不必再讀 postings；查得到就知道要去哪裡讀、要讀多長。dictionary 只有 {{ part1.vocabulary_size|thousands }} 筆，可以整個放在記憶體。

Postings list：含有這個 term 的文件

Postings list 是含有這個 term 的所有 docID，由小到大排好，每篇只記一次。排好序之後，AND 和 OR 都只要兩個指標從頭往後走一次（AND 收下兩邊都有的 docID、OR 收下任一邊的），不用拿每一篇去和另一邊逐一比對。postings 的總量比 dictionary 大得多，最終索引把它存在磁碟上的 postings.bin。

4 · PART 3 · SINGLE-PASS IN-MEMORY INDEXING

SPIMI：直接在記憶體建 dictionary 與 postings

同樣 {{ results.limit_mb }} MB 上限。SPIMI 不產生 pairs、也不需要 termID：dictionary 直接用 term 字串當 key，新 term 約 {{ results.spimi_bytes.entry }} bytes 加上字串本身，之後每多一篇文件只多 {{ results.spimi_bytes.posting }} bytes（postings list 裡的一個指標）。同樣的記憶體能放更多文件，所以只切成 {{ spimi.block_count }} 個 blocks（BSBI 是 {{ bsbi.block_count }} 個）。

1 Read documents sequentially

和 BSBI 一樣依 docID 順序逐篇讀取、做同一套前處理。第 1 個 block 是 Doc {{ spimi.blocks.0.first_doc }}–{{ spimi.blocks.0.last_doc|thousands }}（{{ spimi.blocks.0.docs|thousands }} 篇），是 BSBI 第 1 個 block 的 {% widthratio spimi.blocks.0.docs bsbi.blocks.0.docs 1 %} 倍左右。

  1. BSBI 與 SPIMI 在建立 Inverted Index 時，最大的差異是什麼？
    BSBI 先把每個 token 變成 (termID, docID) pair，排序後才組成 postings；SPIMI 讀到 term 就直接把 docID 加進它的 postings，不產生 pairs、也不需要 termID。結果是記憶體裡放的東西不同：BSBI 這次處理了 {{ bsbi.block_entries|thousands }} 個 pairs（含同一篇的重複），SPIMI 只有 {{ spimi.block_entries|thousands }} 筆 postings；同樣 {{ results.limit_mb }} MB，BSBI 切成 {{ bsbi.block_count }} 個 blocks、SPIMI 只要 {{ spimi.block_count }} 個。最後的索引完全相同（{{ bsbi.final_mb|floatformat:2 }} MB），差別只在建的過程。
  2. 為什麼 BSBI 需要先產生並排序 term-document pairs？
    BSBI 讀文件時是依「文件」的順序拿到 terms，但倒排索引要依「term」整理。把每個 token 變成 (termID, docID) 後依 termID 排序，同一個 term 的所有 docID 才會排在一起、docID 也由小到大，一次掃過去就能組成每個 term 的 postings，並在這時去掉同一篇的重複。用 termID 而不是字串，是因為整數 pair 大小固定、比較快，代價是要一直留著 term → termID 對照表（約 {{ bsbi.term_id_map_mb|floatformat:1 }} MB），合併完再換回 term。這個排序是 BSBI 的主要成本：{{ bsbi.times.sort|floatformat:2 }} 秒，SPIMI 的排序只要 {{ spimi.times.sort|floatformat:2 }} 秒。
  3. SPIMI 如何避免大量 term-document pairs 的排序工作？
    SPIMI 用 dictionary 直接把 docID 放進該 term 的 postings list。文件依 docID 順序讀，所以每個 postings list 加進去時就已經排好序；寫出 block 時只需要排序這個 block 的詞彙（約 {{ spimi.blocks.0.terms|thousands }} 個 terms），不必排序 {{ bsbi.blocks.0.pairs|thousands }} 個 pairs。同一篇文件的重複 term 在加入時就跳過，不會進到記憶體。
  4. 在記憶體有限的情況下，兩種方法如何處理大型文件集合？
    兩者都是「記憶體滿了就把目前的局部索引寫到磁碟、清空，最後再合併」：建 block 時用的記憶體受上限控制，合併時每個 block 只讀目前這一筆。實測把上限從 64 MB 降到 1 MB，BSBI 的 blocks 從 {{ results.limit.64.bsbi.blocks }} 變成 {{ results.limit.1.bsbi.blocks }} 個、SPIMI 從 {{ results.limit.64.spimi.blocks }} 變成 {{ results.limit.1.spimi.blocks }} 個，峰值記憶體大致跟著下降（BSBI {{ results.limit.64.bsbi.peak_mb|floatformat:1 }} → {{ results.limit.2.bsbi.peak_mb|floatformat:1 }} MB（2 MB 上限）、SPIMI {{ results.limit.64.spimi.peak_mb|floatformat:1 }} → {{ results.limit.2.spimi.peak_mb|floatformat:1 }} MB），代價是更多中間檔與更久的合併（BSBI 合併 {{ results.limit.64.bsbi.merge_seconds|floatformat:2 }} → {{ results.limit.1.bsbi.merge_seconds|floatformat:2 }} 秒）。 但上限不是越小越好：降到 1 MB 時 BSBI 有 {{ results.limit.1.bsbi.blocks }} 個 blocks，合併要同時打開 {{ results.limit.1.bsbi.blocks }} 個檔、每個檔都要一個讀取緩衝區（64 KB），峰值反而升到 {{ results.limit.1.bsbi.peak_mb|floatformat:1 }} MB（SPIMI 也從 {{ results.limit.2.spimi.peak_mb|floatformat:1 }} 升到 {{ results.limit.1.spimi.peak_mb|floatformat:1 }} MB）。 另外 BSBI 的峰值在每個上限都比上限高，因為 term → termID 對照表（約 {{ bsbi.term_id_map_mb|floatformat:1 }} MB）不能寫出去，必須一直留在記憶體；SPIMI 沒有這張表，每寫出一個 block 就把 dictionary 整個清空{% if results.spimi_one_block %}，上限 {{ results.spimi_one_block.x|floatformat:0 }} MB 以上整份索引一次放得下（1 個 block，{{ results.spimi_one_block.spimi.peak_mb|floatformat:1 }} MB）{% endif %}。
  5. 哪一種方法在你的實驗中具有較好的執行效率？可能的原因是什麼？
    SPIMI。完整語料 {{ spimi.seconds|floatformat:2 }} 秒 vs BSBI {{ bsbi.seconds|floatformat:2 }} 秒；扣掉兩邊相同的前處理，建索引的部分 BSBI 是 SPIMI 的 {{ results.ratios.index_time|floatformat:1 }} 倍；記憶體峰值 {{ spimi.peak_mb|floatformat:1 }} vs {{ bsbi.peak_mb|floatformat:1 }} MB。原因：(1) BSBI 要排序 {{ bsbi.block_entries|thousands }} 個 pairs，SPIMI 只排序詞彙；(2) BSBI 每個 token 都佔一個 pair（{{ results.pair_bytes }} bytes），SPIMI 每篇文件每個 term 只多 {{ results.spimi_bytes.posting }} bytes，同樣記憶體放得下約 {% widthratio spimi.blocks.0.docs bsbi.blocks.0.docs 1 %} 倍的文件，blocks 少、寫檔與合併的次數也少；(3) 這是 Python 實作，每個 pair 都是一個 tuple 物件，開銷特別大；用 C 寫的 BSBI 每個 pair 只要 8 bytes，兩者的差距應該會比這裡小（推測，沒有實作 C 版本驗證）。
  6. 如果文件數量從 10,000 增加到 100,000，甚至 1,000,000，兩種方法可能會面臨哪些效能問題？
    實測（4 MB 上限）：10,000 → 100,000 → 1,000,000 篇，BSBI {{ results.scale.10000.bsbi.seconds|floatformat:1 }} → {{ results.scale.100000.bsbi.seconds|floatformat:1 }} → {{ results.scale.1000000.bsbi.seconds|floatformat:0 }} 秒、SPIMI {{ results.scale.10000.spimi.seconds|floatformat:1 }} → {{ results.scale.100000.spimi.seconds|floatformat:1 }} → {{ results.scale.1000000.spimi.seconds|floatformat:0 }} 秒，時間大致和文件數成正比；但 blocks 也等比例變多（BSBI {{ results.scale.10000.bsbi.blocks }} → {{ results.scale.100000.bsbi.blocks }} → {{ results.scale.1000000.bsbi.blocks|thousands }} 個，SPIMI {{ results.scale.10000.spimi.blocks }} → {{ results.scale.100000.spimi.blocks }} → {{ results.scale.1000000.spimi.blocks }} 個），會遇到： (1) 合併變重：要同時打開上千個 block 檔，每個檔都要一個讀取緩衝區，BSBI 100,000 篇的峰值已經從 {{ results.scale.full.bsbi.peak_mb|floatformat:1 }} 升到 {{ results.scale.100000.bsbi.peak_mb|floatformat:1 }} MB（SPIMI 維持 {{ results.scale.100000.spimi.peak_mb|floatformat:1 }} MB）。合併時間也比文件數長得快：100,000 → 1,000,000 篇，文件多 10 倍，BSBI 的合併從 {{ results.scale.100000.bsbi.merge_seconds|floatformat:1 }} 變成 {{ results.scale.1000000.bsbi.merge_seconds|floatformat:1 }} 秒，SPIMI 從 {{ results.scale.100000.spimi.merge_seconds|floatformat:1 }} 變成 {{ results.scale.1000000.spimi.merge_seconds|floatformat:1 }} 秒（一般的解釋是 heap 裡的 blocks 越多，每取出一筆要比較的次數也越多）；實務上要分多輪合併或加大記憶體上限。 (2) 中間檔與磁碟 I/O：1,000,000 篇的中間檔約 {{ results.scale.1000000.bsbi.intermediate_mb|floatformat:0 }} MB（BSBI）/ {{ results.scale.1000000.spimi.intermediate_mb|floatformat:0 }} MB（SPIMI），要寫一次再讀一次。 (3) BSBI 的 termID 對照表：這張表不能寫出去，會隨詞彙量一直變大；重複讀的語料不會有新詞，看不出來，用 Heaps' law 推估 1,000,000 篇約 {% for e in results.heaps.estimates %}{% if e.documents == 1000000 %}{{ e.vocabulary|floatformat:0|thousands }} 個詞、對照表約 {{ e.term_id_map_mb|floatformat:0 }} MB{% endif %}{% endfor %}，會吃掉越來越多原本給 pairs 的記憶體。SPIMI 沒有這張表，每個 block 的 dictionary 寫出後就清空。 (4) 前處理（tokenize）佔一半以上的時間，而且和文件數成正比，兩種方法都一樣，可以平行處理。

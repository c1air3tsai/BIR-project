# Project 5 記憶體說明：Baseline、BSBI、SPIMI

這份說明回答三個問題：

1. 三種建索引的方法，記憶體各用在哪裡、差在哪裡？
2. 記憶體會不會影響建索引的速度？
3. 有什麼改善方法？效果多大？

這次作業沒有「訓練」，這裡說的速度都是**建索引的速度**（index construction time）。

**數字來源**
- 主要數字來自 `python manage.py run_indexing_experiments` 的結果：Reuters-21578 全部 21,578 篇，記憶體上限 4 MB，同一設定跑 5 次取中位數，和 `/indexing/` 頁面相同。
- 第 5 節「改善方法」是另外寫的測試程式量的，每種做法跑 3 次取中位數。不同次執行的秒數會差 0.2–0.5 秒，所以**只在同一次測試裡互相比較**。
- 記憶體用 tracemalloc 量，是 Python 在建索引期間配置的記憶體峰值，不含 Python 程式本身與已經讀進來的語料。

---

## 1. 結論

- **Baseline 最快，但記憶體沒有上限。** 整份索引一直放在記憶體，21,578 篇用 18.5 MB，10 萬篇用 56 MB，100 萬篇估計約 473 MB，文件越多用得越多。
- **SPIMI 用的記憶體最少。** 峰值 4.6 MB，大約就是設定的上限，而且文件從 1 萬篇增加到 10 萬篇都沒有變大。
- **BSBI 的記憶體一定比上限高。** 峰值 9.9 MB。它要一直留著 term → termID 對照表（4.2 MB），合併時每個 block 檔還要一個讀取緩衝區。
- **記憶體會影響速度，但不是越多越快。** 上限太小時 blocks 變多，寫檔和合併變慢；BSBI 上限給太大，每個 block 的排序反而變慢。
- **最有效的改善方法：**
  - 縮小每筆資料在記憶體裡的大小：BSBI 的 pair 從 64 bytes 改成 8 bytes，時間少約 20%。
  - 把佔一半以上時間的前處理平行化：4 個 process 讓前處理快 3.2 倍。

---

## 2. 三種方法的記憶體用在哪裡

| | Baseline | BSBI | SPIMI |
|---|---|---|---|
| 記憶體裡放什麼 | 整份索引：term → postings list | 這個 block 的 (termID, docID) pairs ＋ **全域的 term → termID 對照表** | 這個 block 的 dictionary：term → postings list |
| 每多一筆資料 | 每篇文件的每個 term 多 8 bytes | 每個 **token** 多一個 pair：tuple 56 bytes ＋ list 指標 8 bytes ＝ **64 bytes**；同一篇重複的詞也各算一個 | 新 term 約 96 bytes ＋ 字串本身（41 bytes ＋ 字數）；之後每篇文件只多 **8 bytes** |
| 會不會清空 | 不會，全部讀完才寫出 | pairs 每個 block 清空；**對照表一直留著** | 每寫出一個 block 就整個清空 |
| 上限管得到嗎 | 沒有上限 | 只管得到 pairs | 管得到整個 dictionary |
| 合併時 | 不用合併 | 每個 block 檔一個讀取緩衝區（64 KB） | 同左，但 blocks 少得多 |

### 為什麼同樣 4 MB，BSBI 切成 27 個 blocks，SPIMI 只要 7 個？

差別在「每筆資料要多少記憶體」。

- **BSBI**：每個 token 都要 64 bytes，4 MB 只放得下 65,583 個 pairs，大約 800 篇文件。
- **SPIMI**：同一篇文件的同一個詞只記一次，而且每多一篇只要 8 bytes。4 MB 可以放約 185,000 筆 postings，大約 3,400 篇文件。
- **總量也不同**：BSBI 這次處理了 1,730,348 個 pairs（每個 token 一個，含同一篇的重複）。SPIMI 和 Baseline 只有 1,169,501 筆 postings，因為同一篇只記一次。

### 為什麼 BSBI 的峰值（9.9 MB）比上限（4 MB）高？

上限只管得到 pairs，管不到下面兩樣：

1. **term → termID 對照表約 4.2 MB。** 不同 blocks 的 termID 必須一致，所以這張表要從頭留到最後，不能寫到磁碟。詞彙越多，它越大。重複讀的語料不會有新詞，所以實驗裡它停在 51,470 個詞。改用 Heaps' law 推估，100 萬篇的真實語料大約有 38 萬個詞，對照表約 31 MB。
2. **合併時的讀取緩衝區。** 每個 block 檔要一個 64 KB 的緩衝區：27 個 blocks 約 1.7 MB，106 個 blocks 約 6.6 MB，1,223 個 blocks 約 76 MB。所以上限從 2 MB 降到 1 MB 時，BSBI 的峰值反而從 9.8 MB 升到 13.3 MB。

SPIMI 沒有對照表，blocks 也少，所以峰值（4.6 MB）大約就是上限。

### 實測的記憶體峰值（MB）

| 文件數 | Baseline | BSBI | SPIMI |
|---:|---:|---:|---:|
| 2,500 | 3.7 | 5.9 | 3.7 |
| 5,000 | 6.4 | 7.0 | 4.5 |
| 10,000 | 10.3 | 7.7 | 4.5 |
| 21,578（全部） | 18.5 | 9.9 | 4.6 |
| 100,000* | 56.3 | 15.0 | 4.6 |
| 1,000,000* | 約 473（估計） | 沒有量 | 沒有量 |

\* 超過 21,578 篇的部分，是把同一份語料再讀幾輪。這樣不會出現新詞，所以真實的大語料，Baseline 和 BSBI 會比表上更大。

1,000,000 篇沒有用 tracemalloc 量：它會讓建索引慢大約 5 倍，量一次要超過一小時。Baseline 改用 sys.getsizeof 把整份索引的大小加起來估計。這個估計在 21,578 篇是 17.8 MB（實測 18.5 MB），在 10 萬篇是 54.9 MB（實測 56.3 MB），誤差在 4% 以內。

從表上看得出三種方法的成長方式不同：

- **Baseline**：跟著文件數一直長。
- **BSBI**：長得慢一些。增加的部分主要是合併緩衝區（blocks 越來越多）和對照表。
- **SPIMI**：幾乎不變。這正是有記憶體上限的目的。

## 3. 記憶體會不會影響建索引的速度？

**會，但影響有限，而且不是越多越快。** 下表只看「建索引」的時間，扣掉三者都一樣的前處理（每次 2.3–2.8 秒，變動比方法之間的差距還大）。這些都是只跑一次的結果，有 ±0.1–0.2 秒的誤差。

| 記憶體上限 | BSBI 建索引 | BSBI 合併 | BSBI 排序 | SPIMI 建索引 | SPIMI 合併 |
|---:|---:|---:|---:|---:|---:|
| 1 MB | 2.45 秒 | 0.74 | 0.53 | 1.48 秒 | 0.64 |
| 2 MB | 1.89 秒 | 0.52 | 0.53 | 1.09 秒 | 0.39 |
| 4 MB | 1.79 秒 | 0.38 | 0.58 | 0.89 秒 | 0.27 |
| 8 MB | 1.75 秒 | 0.29 | 0.62 | 0.95 秒 | 0.21 |
| 16 MB | 1.80 秒 | 0.24 | 0.68 | 0.84 秒 | 0.15 |
| 32 MB | 2.15 秒 | 0.23 | 0.80 | 0.82 秒 | 0.15 |
| 64 MB | 2.02 秒 | 0.17 | 0.80 | 0.81 秒 | 0.15 |
| 不限制（Baseline） | — | — | — | 0.65 秒 | — |

### (1) 記憶體太少：blocks 變多，寫檔和合併變慢

上限從 4 MB 降到 1 MB：

- BSBI 的 blocks 從 27 個變成 106 個，建索引從 1.79 秒變成 2.45 秒（+37%），合併從 0.38 秒變成 0.74 秒。
- SPIMI 的 blocks 從 7 個變成 50 個，建索引從 0.89 秒變成 1.48 秒（+66%）。

原因是 blocks 越多，要寫的檔案越多，合併時同時打開的檔案也越多。heap 裡要比較的 blocks 越多，每取出一筆要比較的次數也越多（一般的解釋）。

文件數變多時，這個影響更明顯。從 10 萬篇到 100 萬篇，文件多 10 倍：

- BSBI 的合併時間從 1.8 秒變成 24.9 秒（14 倍）。
- SPIMI 從 1.2 秒變成 11.6 秒（10 倍）。

BSBI 的 blocks 多（1,223 個 vs 290 個），所以合併長得比文件數快。

### (2) BSBI 給太多記憶體：排序反而變慢

上限從 8 MB 加到 64 MB 時，BSBI 的合併變快（0.29 → 0.17 秒），排序卻變慢（0.62 → 0.80 秒），加起來反而比較慢（1.75 → 2.02 秒）。

原因是每個 block 的 pairs 變多了。排序的工作量大約是 n log n，一次排很大的 list 比分成很多小段各自排序更花時間；資料超出 CPU 快取時也會變慢（一般的解釋，沒有另外驗證）。

所以 BSBI 有一個比較好的區間，這次是 **4–16 MB**。

SPIMI 只排序每個 block 的詞彙，沒有這個問題：上限越大越快，16 MB 以上整份索引一個 block 就放得下，時間就不再變了。

### (3) 每筆資料要多少記憶體，比上限設多少更重要

BSBI 的 pair 改成緊湊的格式後（第 5 節第 1 項），同樣 4 MB 從 27 個 blocks 變成 4 個，建索引快了將近 1 秒。記憶體的「量」沒變，但同樣的記憶體能放 8 倍的資料。

### (4) 完全不限制記憶體最快，但只適用於放得下的時候

Baseline 建索引只要 0.65 秒，比 SPIMI（0.90 秒）、BSBI（1.80 秒）都快，因為它不用寫 block、不用合併，最後只排序一次詞彙。SPIMI 比 Baseline 多出約 0.25 秒（0.90 vs 0.65 秒），幾乎都是合併的 0.26 秒，這就是「有記憶體上限」的代價。SPIMI 寫 blocks 花 0.14 秒，Baseline 最後寫最終索引花 0.20 秒，這部分兩邊差不多。

代價是 Baseline 的記憶體跟著文件數長：

- 100 萬篇約 473 MB（估計）。
- 真實語料還會一直出現新詞，會更大。

整份索引超過實體記憶體時，作業系統會開始用 swap（拿磁碟當記憶體，慢非常多），或程式直接出現 MemoryError。這是一般常見的情況，這台電腦有 8 GB，實驗裡沒有遇到，所以沒有實測。BSBI 和 SPIMI 就是為了這種情況設計的：用一點速度，換「記憶體用量固定、不會跟著文件數長」。

### (5) 垃圾回收（GC）不是原因

BSBI 每個 pair 都是一個 tuple，會被 Python 的垃圾回收器追蹤。建一次索引會觸發 2,378 次 GC，SPIMI 只有 179 次。

但把 GC 關掉後並沒有變快（BSBI 4.66 秒 vs 4.81 秒，SPIMI 3.40 秒 vs 3.42 秒，都在誤差範圍內）。所以 BSBI 慢不是因為 GC，而是排序和比較多的 blocks。

### (6) 真正最花時間的是前處理

前處理（tokenize、轉小寫、去 stopword）在三種方法都是 2.3–2.5 秒，佔總時間的 56%（BSBI）到 80%（Baseline）。記憶體相關的差異只影響剩下的部分：BSBI 和 SPIMI 總時間差 0.8 秒，其中幾乎全部來自建索引的部分。

---

## 4. 小結：三種方法的取捨

| | 速度 | 記憶體 | 適合 |
|---|---|---|---|
| Baseline | 最快（建索引 0.65 秒） | 跟著文件數長，沒有上限 | 文件少、記憶體確定放得下 |
| SPIMI | 次快（0.90 秒） | 固定在上限附近（4.6 MB） | 文件多、記憶體有限（大多數情況） |
| BSBI | 最慢（1.80 秒） | 比上限高，還會隨詞彙量和 blocks 數變大（9.9 MB） | 一定要用固定長度、可以直接排序的整數資料時，例如交給外部排序工具或 C 程式處理（一般的說法，這次沒有實作驗證） |

## 5. 改善方法（實測）

| # | 做法 | 解決什麼 | 實測結果 | 代價 / 注意 |
|---|---|---|---|---|
| 1 | **BSBI 用緊湊的 pair**：把 (termID, docID) 合成一個 64-bit 整數（termID × 2³² ＋ docID），存在 array 裡，用 numpy 排序 | pair 太大（64 bytes）→ blocks 多、排序慢 | 每個 pair 64 → 8 bytes；同樣 4 MB，blocks 27 → 4；總時間 4.70 → 3.74 秒；排序 0.78 → 0.11 秒；合併 0.41 → 0.19 秒；建出來的索引和原本完全相同 | numpy 排序與去重複時會複製陣列，峰值反而從 9.9 升到 17.6 MB。可以改成就地排序，或只把一半的上限給 pairs，另一半留給排序（推測，沒有實測） |
| 2 | **SPIMI 的 postings 用 array('I')**：每個 docID 存成 4 bytes 的整數，list 每格是 8 bytes 的指標 | postings 佔的記憶體 | 時間不變（3.52 vs 3.53 秒）；4 MB 上限時峰值 4.6 → 4.2 MB、blocks 7 → 6；不限制記憶體時 18.5 → 13.7 MB（少 26%） | 改動很小；省下的比例會隨 postings 變長而變大 |
| 3 | **合併時調整讀取緩衝區**：blocks 多時每個緩衝區給小一點，或限制一次合併的檔案數（分多輪合併） | blocks 多時合併的記憶體 | BSBI 上限 1 MB（106 個 blocks）：緩衝區 64 KB → 8 KB，峰值 13.3 → 7.4 MB，合併時間不變（都是 0.69 秒） | 緩衝區太小時讀檔次數變多。分多輪合併能把同時打開的檔案數控制住，代價是資料要多讀寫一輪（一般的做法，沒有實測） |
| 4 | **記憶體上限選中間值** | blocks 太多或排序太大 | BSBI 在 4–16 MB 最快（1.75–1.80 秒）；SPIMI 4 MB 以上就差不多（0.81–0.95 秒） | 最好的值會隨資料量和電腦不同，要實際量 |
| 5 | **壓縮 postings**：存相鄰 docID 的差（gap），再用 variable-byte 編碼（小的數字用 1 byte） | 中間檔與最終索引太大、磁碟讀寫多 | 最終索引的 postings 4.46 → 1.43 MB（只剩 32%） | 讀寫時要編碼、解碼，會多一點 CPU 時間（沒有實測）；中間檔也能用同樣的方法縮小 |
| 6 | **前處理平行化**：用 4 個 process 同時 tokenize | 佔一半以上時間的前處理 | 2.53 → 0.78 秒（快 3.2 倍） | 每個 process 都要自己的記憶體；三種方法都適用，是最划算的改善 |
| 7 | 關掉垃圾回收（GC） | 大量 tuple 觸發 GC | 沒有變快（見第 3 節第 5 點） | 不建議，沒有效果 |
| 8 | BSBI 的 term → termID 對照表太大時，改用 SPIMI；或把對照表依字首分成幾份放磁碟 | 對照表隨詞彙量變大 | 沒有實測（Heaps' law 推估 100 萬篇約 31 MB） | 分散對照表會讓查 termID 變慢（推測） |

### 優先順序建議

1. **先平行化前處理（第 6 項）**：它佔的時間最多，改了三種方法都受惠。
2. **選 SPIMI，或把 BSBI 的 pair 改成緊湊格式（第 1 項）**：直接減少 blocks 和排序時間。
3. **資料很大時，壓縮 postings（第 5 項）並控制合併的檔案數（第 3 項）**：這時磁碟讀寫和合併會變成主要成本。

## 6. 報告時可以這樣說

> Baseline 把整份索引放在記憶體，最快，但記憶體跟著文件數成長：21,578 篇 18.5 MB、10 萬篇 56 MB、100 萬篇約 473 MB。BSBI 和 SPIMI 用固定的記憶體上限，把索引分成 blocks 寫到磁碟再合併，記憶體不會跟著文件數長，代價是寫檔與合併的時間。
>
> 同樣 4 MB，SPIMI 每筆 posting 只要 8 bytes、同一篇只記一次，所以 blocks 少（7 vs 27）、峰值低（4.6 vs 9.9 MB）、也比較快。BSBI 每個 token 都佔 64 bytes 的 pair，還要一直留著 termID 對照表。
>
> 記憶體會影響速度，但不是越多越快：上限太小時 blocks 多、合併慢；BSBI 上限太大時排序變慢，這次在 4–16 MB 最快。實測最有效的改善，是把 pair 改成 8 bytes 的緊湊格式（快約 20%），以及把佔一半以上時間的前處理平行化（快 3.2 倍）。
